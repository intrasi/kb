# Obfuscation Techniques & Engines: AI-Resistance and Weekend Usability

> Scope note: This dossier goes *beyond* two existing team files — `AI_RE_Benchmark_Hackathon_Summary.md` §9 (weekend-usable engine table) and `Open Agentic Resilience Benchmark...md` §B (engine table). Those cover the engines at a one-line-per-row level and the measured LLM-vs-obfuscation numbers (Promon, Deconstructing Obfuscation, Thales). This file adds: (a) technique-by-technique depth with overhead and behavior-change risk, (b) a corrected LLM-resistance ranking with the underlying evidence, (c) exact 48h usage per engine incl. which are *genuinely* `-fpass-plugin`-loadable vs which require a source build (the team table overstates this), (d) the MBA-vs-SMT tension, and (e) pitfalls. Where this file contradicts the team files, it is flagged.

## Technique catalogue: what each does, overhead, behavior-change risk

### Takeaway
Techniques split into "data-level" (renaming, string/constant encryption, MBA) and "control-level" (dead code, BCF, CFF, virtualization, self-modifying) plus a "runtime/defensive" family (anti-debug, anti-tamper/RASP, environment binding, white-box crypto). Overhead ranges from ~0 (renaming) to 42×–247× (Tigress virtualization). Behavior-change risk is low for renaming/string-enc, moderate for CFF/MBA (constant-time and FP edge cases), and highest for virtualization and self-modifying code (where correctness and platform assumptions break most often).

### Cited Findings (per technique)
- **Identifier renaming / symbol stripping** — removes names (`hash_djb2` → `sub_401000`). Overhead ≈ 0 runtime/size. Behavior risk: none. Implemented by ProGuard/R8 (JVM/Android), `strip`, OLLVM has no dedicated pass (it's a linker/build-tool step). Barely dents frontier LLMs: GPT-4.1 kept 90.0% Pass@1 on renamed/dead-branch/symbol-stripped inputs vs 92.9% plain — [Robustness of Code LLMs on Protected Code, arXiv 2609.04220](https://arxiv.org/abs/2609.04220) (cited in team §5). Use as a *weak-control row*, not a defense.
- **String / constant encryption** — literals stored encrypted, decrypted at use. OLLVM forks: `-sobf` (DreamSoule), `gvenc` (Polaris), `strenc`/`constenc` (xollvm), `kagura-str`/`kagura-str-aes` (kagura). Overhead: small (a decrypt stub per string + runtime decrypt). Behavior risk: low, but ctor-time vs use-time decryption matters (Polaris decrypts in-function, not `.ctor`, to avoid a global-init dump point — [za233/Polaris-Obfuscator](https://github.com/za233/Polaris-Obfuscator)). xollvm default cipher is now ChaCha20 (was AES-128-CTR), tableless/no host-endian assumptions — [und3ath/xollvm](https://github.com/und3ath/xollvm). Elastic study: `EncodeLiterals` alone solved cheaply ($1.65) — strings alone are weak — [Elastic Security Labs](https://www.elastic.co/security-labs/threat-command/llm-reversing-vs-llm-obfuscation).
- **Dead-code / junk insertion** — inserts unreachable or no-effect code. Overhead: size up, runtime ~flat (dead paths not executed). Behavior risk: low. Weak vs LLMs (they prune it) — part of the "barely dents" set in [arXiv 2609.04220](https://arxiv.org/abs/2609.04220).
- **Bogus control flow (BCF) / opaque predicates** — adds fake branches guarded by predicates that are always true/false but hard to prove statically. OLLVM `-bcf` (`-bcf_loop=N`, `-bcf_prob`). Overhead: moderate (extra blocks + predicate computation on real paths). Behavior risk: low if predicates are truly opaque; a mis-synthesized predicate can change control flow. LLM resistance: *highly model-dependent* (see ranking below).
- **Control-flow flattening (CFF)** — collapses the CFG into a single `switch`-in-`while` dispatcher keyed by a state variable ("pc"). OLLVM `-fla`; Polaris `fla` (enhanced: XOR-encrypted state dispatch keyed per-block from the dominator tree, so you can't grep plaintext case constants — [za233/Polaris](https://github.com/za233/Polaris-Obfuscator)); Tigress `--Transform=Flatten` with `--FlattenDispatch=switch|goto|indirect`. Overhead: moderate-to-high; inflates function size substantially (Elastic attributes the Flatten+MBA cost jump to "flattening inflating function size"). Behavior risk: low-moderate; proven to *preserve* constant-time policy — [arXiv 2003.05836](https://arxiv.org/pdf/2003.05836) — so it's safe for crypto hot paths in that respect.
- **Instruction substitution (SUB) / MBA** — replaces simple ops with equivalent longer sequences; MBA mixes boolean and arithmetic operators (`x+y` → `(x^y)+2*(x&y)`). OLLVM `-sub` (`-sub_loop=N`); xollvm `mba`/`substitution`; Tigress `--Transform=EncodeArithmetic` (MBA) and `EncodeData`/`EncodeLiterals`. Overhead: low-moderate (more instructions, no new control flow). Behavior risk: low for integer identities; FP and overflow-wrapping edge cases can diverge if the identity isn't exact. Strongest single technique vs LLMs (see ranking + MBA section).
- **Virtualization / VM-based** — compiles a function into bytecode for a bespoke interpreter embedded in the binary. Tigress `--Transform=Virtualize` (dispatch: `switch|direct|indirect|call|ifnest|linear|binary|interpolation`); xollvm `vm`; kagura VM (topic-listed); XuanJia (research, binary-level). Overhead: **highest — Tigress virtualization 42×–247× runtime** ([XuanJia, arXiv 2601.10261](https://arxiv.org/abs/2601.10261), measured against Tigress v4.0.10). Behavior risk: highest (interpreter bugs, exception-handling/ABI breakage — XuanJia's whole contribution is "ABI-Compliant EH Shadowing" to stop VM obfuscation breaking exception handling). Strongest static defense but reserve for tiny non-hot functions.
- **Self-modifying code (SMC)** — code rewrites itself at runtime (packing, JIT). Tigress `--Transform=Jit` / `JitDynamic`. Overhead: high + requires W^X exceptions. Behavior risk: high (breaks on hardened/NX platforms, signing). Elastic: `Jit` was *the most effective single transform* — failed the agent at $5.90/32min; `JitDynamic` also failed — [Elastic](https://www.elastic.co/security-labs/threat-command/llm-reversing-vs-llm-obfuscation).
- **Anti-debug / anti-tamper / RASP** — runtime detection of debuggers, hooks (Frida), emulators; integrity checksums; respond by crashing or (better) corrupting. kagura: `kagura-anti-debug` (hook/breakpoint detection), `kagura-tamper` (startup function checksums), Magisk/Zygisk/LSPosed/jailbreak detection. Shellsmith (Rust, Android RASP). Overhead: small per-check. Behavior risk: false positives on legit debug/analytics tooling. Note: crash-on-detect is a *weak* design vs agents — see pitfalls.
- **Environment binding** — key/secret derived from device/runtime values so code only runs in the intended environment. This is the Quarkslab-recommended pattern (mix sensor values into key material instead of branching). Overhead: small. Behavior risk: brittle across environments. (Attack behavior covered in team §6.)
- **White-box cryptography** — embeds a key inside the cipher implementation so it's never in memory as a key. Overhead: large tables / slow. Behavior risk: implementation-specific; many WBC schemes are academically broken. **No mature open-source library** bundles WBC — it's the proprietary piece even ASPIRE excludes; commercial only (DexGuard) — [arXiv 2606.14233 survey context](https://arxiv.org/html/2606.14233v1), [ASPIRE arXiv 2003.00916](https://arxiv.org/pdf/2003.00916). Out of scope for a weekend defense matrix.

### Inferences
- For the benchmark matrix, overhead and behavior risk cluster cleanly: cheap+safe (rename, string-enc, dead code, SUB/MBA), moderate (BCF, CFF), expensive+risky (virtualization, SMC, WBC). Put MBA and SUB as the "cheap but strong" headline cells and virtualization as the "strong but 100×-overhead" ceiling cell — this is exactly the lift-vs-overhead Pareto the team wants to plot.

### Gaps
- No single open-source WBC tool to drop into the matrix; would require writing one or using a toy AES-WBC, which isn't representative. Recommend excluding WBC or flagging it "commercial-only, not evaluated."

## Which techniques resist LLMs best? (corrected ranking + evidence)

### Takeaway
Ordering by single-technique resistance to frontier LLMs: **instruction substitution / MBA (high) > BCF (variable, model-dependent) > CFF (low — LLMs undo flattening easily) > renaming/dead-code (negligible)**. **Combined techniques = near-universal failure.** NOTE — this *partially corrects* the team summary, which wrote "CFF moderate; BCF low." The strongest primary source (Deconstructing Obfuscation) shows the opposite for single passes: CFF is the *easiest* for most LLMs to defeat, while BCF is the most variable. The team's instinct is right only once passes are *combined* (CFF's value is as a cost-multiplier, not a standalone wall).

### Cited Findings
- **Deconstructing Obfuscation ([arXiv 2505.19887](https://arxiv.org/html/2505.19887v1), OLLVM, 7+ frontier models).** Table 2 scores *attacker difficulty / human-intervention needed* 0 (trivial) to 5 (beyond expert correction). Per-technique (higher = more resistant):
  - **CFF/Flattening: 0–1 for almost every model** (GPT-4o 1, GPT-4.5 0, o1 0, Grok 3 0, Claude 3.7 0–1). → LLMs flatten-reverse easily. *Lowest single-technique resistance.*
  - **BCF: 0 (Claude 3.7) to 5 (DeepSeek R1)** — wildly model-dependent; GPT-4o 4, o3-mini 4–5, Grok 3 just 1. (Text/table are internally inconsistent: §3.1 says only Claude 3.7 solved BCF first-try, table disagrees.)
  - **Instruction substitution (IS): 4–5 across models** (GPT-4o 4, GPT-4.5 4, DeepSeek R1 5, Grok 3 4; Claude 3.7 an outlier at 1–2). *Highest single-technique resistance.*
  - **All-combined: level 5 for every applicable model** ("universal failure"), i.e. GPT-4.5, o1, DeepSeek R1, Grok 3, Claude 3.7 all 5.
  - Obfuscator = Obfuscator-LLVM; flags per technique in their §2.
- **Promon ATR Q1 2026** (team §5, zero-shot, OLLVM, ARM/x86): three-pass SUB+FLA+BCF dropped average success to **8.5%** on ARM assembly; FLA+BCF amplified complexity **4.18× (x86) / 5.50× (ARM)** over BCF alone (multiplicative). This is the evidence that *CFF earns its keep only in combination* — [Promon ATR, Zenodo 10.5281/zenodo.18377774].
- **Elastic Security Labs (Claude Opus 4.6, Tigress, static-only, small n)** — [Elastic](https://www.elastic.co/security-labs/threat-command/llm-reversing-vs-llm-obfuscation):
  - **MBA (EncodeArithmetic) weakest alone** — solved at $0.47; hardening only 1.5× cost. (Contrast with academic claim that MBA is strongest — see tension below; difference is static-only Opus-4.6 vs the models in 2505.19887, and Tigress MBA default strength.)
  - **Flatten(indirect) alone** solved at $1.27; but **Flatten+MBA hardened = biggest jump, 4.5× cost / 4.3× time** — combination effect again.
  - **Virtualize(indirect,regs)** solved at $6.00/25min; **double virtualization failed**; **Jit failed** ($5.90). Phase 3 combined passes = **0% solved**.
  - Baseline unobfuscated cost $0.43; successes averaged $2.39, failures $4.83.
- **LLM4Decompile under obfuscation** (team §5, [arXiv 2403.05286](https://arxiv.org/abs/2403.05286)): best fine-tuned decompiler dropped **90.2% under CFF** and **78.0% under BCF** — but this is a *fine-tuned narrow decompiler*, not an agent; it is brittle where frontier agents are not. Don't conflate.

### Inferences
- The honest headline for the pitch: **"single passes are a speed bump (frontier LLMs beat CFF/BCF/rename); the wall is combination and instruction-level data obfuscation (SUB/MBA), and the cost — not impossibility — is what you sell."** This reconciles all three sources: academic difficulty-levels (combined=5), Promon's 8.5% (3-pass), and Elastic's 0% on phase-3 combined.
- CFF should be framed in the matrix as a *multiplier* row (FLA+BCF, FLA+MBA), not a standalone defense, because every source agrees it's weak alone but strong combined.
- Model-dependence of BCF (0 for Claude, 5 for DeepSeek) means per-model reporting is mandatory — a single aggregate number hides a 5-level spread.

### Gaps
- Deconstructing Obfuscation gives *ordinal difficulty levels, not success percentages*; its scale and text are internally inconsistent (flagged). Treat as directional, not precise.
- Elastic is small-sample, single-run, static-analysis-only, one model (Opus 4.6) — directional. Its "MBA weakest" finding conflicts with the academic "MBA strongest" framing; the resolution is that Tigress's *default* EncodeArithmetic is a mild MBA, and agentic Opus simplified it, whereas hardened/deep MBA resists SMT (next section).

## MBA specifically: resists AI AND defeats SMT equivalence solvers

### Takeaway
MBA's power is that mixing boolean and arithmetic operators breaks the algebraic reduction rules (commutation/association/distribution) that both human intuition and automated simplifiers rely on — so it simultaneously confuses LLMs *and* makes SMT-based equivalence proving blow up. This is a real tension for this project: the team's own earlier "formal verification of semantic equivalence" idea relies on exactly the SMT equivalence checks that MBA is designed to defeat.

### Cited Findings
- **Root cause:** mixing two heterogeneous operator classes breaks regular reduction rules (commutation, association, distribution); SAT solvers, boolean minimizers, and computer-algebra systems each handle only one class, so none simplifies mixed expressions — [Defeating MBA-based Obfuscation (ResearchGate)](https://www.researchgate.net/publication/309501815_Defeating_MBA-based_Obfuscation), [MBA-Blast, USENIX Sec '21](https://www.usenix.org/system/files/sec21fall-liu-binbin.pdf).
- **SMT blow-up is deliberate & patentable:** an MBA opaque predicate can be built specifically "to stress the internal bitblasting algorithm within an SMT-solver," turning a quick equality check into an intractable one — [USPTO 12585460](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12585460).
- **Even state-of-the-art MBA deobfuscators still depend on SMT and don't terminate on hard inputs:** current simplifiers "cannot effectively simplify expressions which utilize constants inside of their bitwise operators ... cannot be simplified soundly ... unless an SMT solver is used," and synthesis-based ProMBA "must resort to ... verification via SMT solving, which cannot be expected to terminate in a reasonable time on complex inputs" — [Deobfuscation of Semi-Linear MBA, arXiv 2406.10016](https://arxiv.org/pdf/2406.10016).
- **Nonlinear MBA defeats equivalence proving:** "SMT solvers may struggle to prove equivalence between two expressions if any involves certain complex (non-)polynomial MBAs" — [CCS'23 program-synthesis paper](https://psl.hanyang.ac.kr/assets/pdf/ccs23.pdf); see also [GAMBA, arXiv 2305.06763](https://arxiv.org/pdf/2305.06763) (handles general linear MBA but not arbitrary nonlinear).
- **The counter-evidence (don't oversell):** linear and semi-linear MBA is now routinely simplified by MBA-Blast, MBA-Solver, SiMBA, GAMBA, ProMBA. So *shallow* MBA (OLLVM `-sub` single-pass, Tigress default EncodeArithmetic) is beatable — consistent with Elastic's "MBA weakest alone, $0.47." Depth, nonlinearity, and constants-in-bitwise-ops are what keep it hard.

### Inferences
- For the matrix: use MBA at *depth* (xollvm `mba(maxDepth=3)` or stacked `-sub_loop=3`) and pair with CFF so the attacker can't isolate the expression. Report it as the "cheap, SMT-hostile, behavior-safe" cell.
- Project tension to document explicitly: any grader that tries to *prove* semantic equivalence via SMT (the abandoned formal-verification idea) will itself choke on MBA-protected programs. This is *why* the team pivoted to differential-fuzzing grading — MBA is the concrete reason SMT equivalence doesn't scale here. Worth stating in the pitch as a "why formal verification is the wrong grader" point.

### Gaps
- No single number for "how deep must MBA be to beat solver X in time T" — it's input-specific. Can't give a clean threshold.

## Engines & exact 48h usage — which are really `-fpass-plugin`

### Takeaway
**Only xollvm and kagura are genuinely loadable `-fpass-plugin` (no LLVM source build).** The team tables in §9/§B imply DreamSoule/ollvm17 and Polaris are plugin-loadable "forks you don't build" — that is wrong: both require patching the LLVM source tree and a multi-hour full LLVM build. For a weekend, lead with **xollvm (stock LLVM 22/23 plugin)** or **kagura (LLVM 17–22 plugin/driver)**; keep ollvm17/Polaris only if you pre-build or use a CI image; keep **Tigress** as source-to-source (no LLVM at all) for virtualization.

### Cited Findings
- **xollvm (und3ath)** — [github.com/und3ath/xollvm](https://github.com/und3ath/xollvm), Apache-2.0-with-LLVM-exception. Stock **LLVM 22/23**, New Pass Manager, zero source edits; ships `Obfuscator.so` for `-fpass-plugin` (Linux/macOS; Windows uses linked `kagura`-style tool). Passes: `constenc, mba, substitution, vcall, split, sdiff, bcf, flattening, shield, adec` (anti-decompiler: indirectbr trampolines + asm junk + pointer aliasing), `vm` (full-function bytecode), module-level `strenc` and `fmerge` (merge functions sharing `group=`). **Usage:**
  - `opt -load-pass-plugin=./Obfuscator-linux-x64.so -passes=obfuscation test.ll -S -o test.obf.ll`
  - `clang -fpass-plugin=./Obfuscator-linux-x64.so ...`
  - Build plugin only: `cmake -S xollvm -B build -G Ninja -DLLVM_DIR=/usr/lib/llvm-22/lib/cmake/llvm && ninja -C build Obfuscator`
  - Config is **source annotations**: `__attribute__((annotate("obf: mba(prob=70,maxDepth=3), substitution(loop=2)")))`; VM: `annotate("obf: vm(hardened=1,useAES=1,regEncrypt=1)")`.
  - Reproducibility: `-obf-seed=N -obf-deterministic -obf-seed-manifest=seeds.json`; diagnostics `-passes=obf-dump-config` and `-passes=obf-metrics` (JSONL — useful for the overhead column).
  - **Documented conflict: `vm` vs `flattening` (both restructure CFG — pick one per function); `fmerge` always runs first.** The `-obf-all` global-selection PR exists (slowriot #38).
- **kagura (qusamulab)** — [github.com/qusamulab/kagura](https://github.com/qusamulab/kagura), MIT. **LLVM 17–22** NPM, `-fpass-plugin` loadable (Windows linked into `kagura-opt` since `-fpass-plugin` is unavailable there). Passes: `kagura-str` (XOR), `kagura-str-aes`, `kagura-fla`, `kagura-bcf`, `kagura-mvo`/`kagura-pe` (per-load/store XOR via `Protected<T>` runtime), `kagura-anti-debug`, `kagura-tamper` (startup checksums), `kagura-ci` (runtime-resolved call thunks); VM virtualization topic-listed. Platforms: iOS/Android/macOS/Windows/Linux/Wasm. **Usage** via JSON-config driver: `build/bin/kagura -kagura-config=kagura.json -O1 your_file.c -o your_file`; config `{"profile":"BALANCED","passes":{"str":true,"fla":true,"bcf":true,"mvo":true},"tuning":{"bcf_prob":40,"seed":12345}}`. Needs matching upstream LLVM 17–22 toolchain + Python 3.9+. **Caveat on 17–21: clang parses `-mllvm` before `-fpass-plugin` loads, so use the shipped `opt`/driver, not `-mllvm`.**
- **DreamSoule/ollvm17** — [github.com/DreamSoule/ollvm17](https://github.com/DreamSoule/ollvm17), based on **LLVM 17.0.6**. **NOT a `-fpass-plugin`** — it patches the source tree (`PassBuilder.cpp`, `CMakeLists.txt`) and uses `-mllvm` flags; requires a full LLVM build. Passes: `-fla`, `-bcf` (`-bcf_loop`, `-bcf_prob`), `-sub` (`-sub_loop`), `-split` (`-split_num`), `-sobf` (narrow-char string enc, CLI-only no annotation), `-icall`, `-ibr`, `-igv` (indirect call/branch/global). Typical: `-mllvm -bcf_loop=3 -mllvm -sobf -mllvm -sub -mllvm -sub_loop=3 -mllvm -split -mllvm -split_num=5`.
- **za233/Polaris-Obfuscator** — [github.com/za233/Polaris-Obfuscator](https://github.com/za233/Polaris-Obfuscator), **LLVM 16.0.6**, successor to Pluto. **Source-tree build required** (copy `llvm` folder in, rebuild). Flags `-mllvm -fla` (encrypted-state flattening resisting local symbolic exec), `-mllvm -gvenc` (global/string enc, in-function not `.ctor`), plus indirect call/branch, alias access, BCF, and **MIR-level** passes (dirty bytes, MIR substitution) that make IDA's decompiler hallucinate variables — [ICSE26 Polaris paper](https://ttfish.cc/content/Papers/ICSE26-Polaris.pdf). Strongest free *decompiler-degradation*, but heaviest setup. (A Python-on-LLVM-21 port of its 9 passes exists via expend20.)
- **Tigress** — [tigress.wtf/usage.html](https://tigress.wtf/usage.html), Univ. of Arizona, **free for non-profit research only; commercial needs a UA licence; not OSS**. Source-to-source C (no LLVM). `--Transform=` `Virtualize` (dispatch `switch|direct|indirect|call|ifnest|linear|binary`), `Flatten` (`--FlattenDispatch`, `--FlattenOpaqueStructs`), `EncodeArithmetic` (MBA), `EncodeLiterals`, `EncodeData`, `Jit`/`JitDynamic` (self-modifying), `AntiAliasAnalysis`, `Split`. Chain in one command: `tigress --Environment=x86_64:Linux:Gcc:4.6 --Transform=Virtualize --Functions=f --VirtualizeDispatch=direct --Transform=Flatten --Functions=f --Transform=EncodeArithmetic --Functions=main --out=o.c in.c`. **Overhead: virtualization 42×–247× runtime** ([XuanJia arXiv 2601.10261](https://arxiv.org/abs/2601.10261), vs Tigress v4.0.10). Report overhead next to every Tigress cell. Common chains: Virtualize→Flatten, Flatten→AntiAliasAnalysis→Flatten.
- **JS track:** [javascript-obfuscator](https://github.com/javascript-obfuscator/javascript-obfuscator) (BSD-2): string-array enc, CFF, dead code, self-defending, debug-protection; Obfuscator.io `vm-anti-llm` preset. README admits no LLM-specific defenses (team §4). **Android/JVM:** ProGuard/R8 (GPL, rename+shrink only — weak-control row); DexGuard (commercial: RASP, polymorphic, data enc, native hardening) — [arXiv 2606.14233](https://arxiv.org/html/2606.14233v1).
- **RASP/anti-debug open source (2026):** kagura (above) and **Shellsmith** (Rust, Android RASP/APK protection) — the only fresh open RASP projects; full WBC+RASP combos remain commercial.

### Inferences
- **48h recommended stack:** xollvm `.so` (LLVM 22 plugin) as the primary engine for the OLLVM-family matrix rows (sub/mba/bcf/fla/strenc/vm, all seedable + emits JSONL metrics for the overhead column), **plus** Tigress source-to-source for the Virtualize ceiling row (no LLVM build, just a download + non-profit licence). This gets every lever in the team's §11 matrix (none / rename+strip / sub / fla / bcf / fla+bcf / sub+fla+bcf / +string-enc / Virtualize) without a single full LLVM build.
- Correct the team §9/§B tables: move DreamSoule/ollvm17 and Polaris from "loadable plugin forks" to "source-build forks"; promote xollvm/kagura as the actual plugin options. This matters because a from-source LLVM build can eat most of Day 1.
- Annotation-driven config (xollvm) is *ideal* for per-function matrices (protect only the secret function, leave hot paths clean) — directly supports the team's "flatten sensitive functions, not the whole hot path" need.

### Gaps
- Couldn't confirm xollvm/kagura prebuilt `.so` availability for LLVM 22 on the exact hackathon OS/arch — may still need the (fast, ~minutes) plugin-only `cmake+ninja` build against an installed LLVM, not a full LLVM build. Verify before Day 1.
- Kotoamatsukami and Hikari (team §9) not re-verified here; awesome-ollvm ([lich4/awesome-ollvm](https://github.com/lich4/awesome-ollvm)) is the live index to check their current LLVM version and plugin status.

## Known pitfalls: diminishing returns, cancellation, conflicts, hot paths

### Takeaway
The main traps: (1) CFF and VM both restructure the CFG and conflict — never stack them on one function; (2) virtualization/self-modifying on hot paths is catastrophic (42×–247×); (3) single passes have sharply diminishing returns vs frontier LLMs while combination multiplies cost; (4) crash-on-detect anti-tamper is a weak design against agents; (5) some passes are mechanically reversible by known IDA scripts.

### Cited Findings
- **vm ⟂ flattening conflict** — both restructure the CFG; xollvm explicitly documents "use one or the other per function" — [und3ath/xollvm](https://github.com/und3ath/xollvm). Stacking produces either a build failure or a VM wrapping a dispatcher (double overhead, little added resistance).
- **Hot-path cost** — "flatten the sensitive functions rather than an entire hot-path codebase" (overhead real though often negligible per-function) — [bytehide control-flow obfuscation](https://bytehide.com/platform/shield/obfuscation/control-flow-obfuscation). Tigress virtualization 42×–247× ([arXiv 2601.10261](https://arxiv.org/abs/2601.10261)) makes whole-program VM a non-starter on anything latency-sensitive.
- **Combination > repetition (multiplicative, not additive)** — Promon FLA+BCF amplified complexity 4.18×/5.50× over BCF alone (team §5); Elastic Flatten+MBA hardened = 4.5× cost vs Flatten alone 1.0×. But **single-pass hardening barely moved the needle** (Tigress MBA hardening only 1.5× cost, virtualization hardening 0.8× — i.e. *negative*) — [Elastic](https://www.elastic.co/security-labs/threat-command/llm-reversing-vs-llm-obfuscation). → stacking *different* techniques pays; re-running the *same* pass harder often doesn't.
- **Compiler can undo source-level obfuscation** — Tigress works on source, so the C compiler's constant-propagation/DCE can partially re-simplify after obfuscation ([XuanJia arXiv 2601.10261](https://arxiv.org/abs/2601.10261) notes this as why Tigress overhead is lower than binary-level VM). Compile Tigress output at `-O0`/`-O1` or the optimizer erodes the protection.
- **Mechanical reversibility** — OLLVM `-fla`/`-bcf` have public IDA Python deobfuscation scripts that exploit the fixed pass structure; plain OLLVM flattening is pattern-removable — [awesome-ollvm](https://github.com/lich4/awesome-ollvm) (IDA deobf plugins listed). Polaris's encrypted-state dispatch exists specifically to defeat the "grep the plaintext case constants" attack that beats stock OLLVM flattening.
- **Crash-on-detect is weak vs agents** — Quarkslab recipe (team §6): agents route around protections via emulation and never-crash-return-plausible-wrong-answer beats crash-based anti-tamper. Anti-debug/RASP that *branches* on a sensor is defeated; mixing the sensor into key material is not.
- **False-confidence as a lever, not just a risk** — Elastic Double Fond: the model "accepted the decoy logic" (1/5 with hint, 0/5 blind); Dispatch Maze V2 unsolved at 3.4× cost — misdirection that exploits plan-persistence is cheap and effective, but fragile/single-run.

### Inferences
- Matrix hygiene: enforce "at most one CFG-restructuring pass per function" (fla XOR vm); apply virtualization only to small non-hot secret functions; always report overhead (xollvm JSONL / wall-clock) in the same cell as lift so the Pareto frontier is visible.
- Expect *single-technique rows to look weak* (that's the honest finding) and *combination rows to carry the headline*. Budget frontier-model runs for the combined cells; use cheap models for single-pass search.
- Compile-after-Tigress at low `-O` and verify the obfuscation survived (diff instruction counts) — a silent `-O2` re-simplification would understate Tigress in the results.
